# 结果观察不是真值，画像只能经受控研究与人工发布改变

招聘决定继续由 ApplicationCase 拥有；G3 将 Offer、入职、留任和任职表现保存为带来源、时间、岗位与用途的可纠正来源断言，并在一个不含来源系统的对账键下形成当前 Outcome Observation 解析，再按版本化规则形成 Outcome Label。画像候选修订必须先仅用 discovery/train/dev 输入形成并冻结内容哈希，随后才能预注册使用未打开确认性 holdout 的 Feedback Study；同一 holdout 不得既生成又验证候选。

任何观察、标签、离线评测或 Agent Run 都不能直接改变画像。只有当前 D0–D4 发布资格全部通过且未过期、Hiring Owner 与 HRBP / Profile Governance Owner 两个不同人类主体批准同一候选修订/研究/范围、并由有权限的人单独授权发布后，确定性控制面才能先准备不可变 Profile Version、完成关键下游同步，再原子提交未来案件使用的权威指针。观察纠正、删除、用途变化或 P0 风险发生时，系统先提升安全世代并冻结新案件引用、使待发布物失效，再由人决定重做研究或授权回滚到此前已批准版本；回滚后画像自动化只回到 A0。

## Considered Options

- 按历史面试通过率或录用率每周自动调权：反馈快，但会把旧流程偏差、幸存者偏差和人为决定放大成“真值”。
- 由 Agent 生成建议并由单一 Owner 一键生效：保留部分人审，但无法独立审查样本、用途、公平和影响范围，也会混淆批准、同步和生效。
- 来源断言、当前解析、标签、队列、预研究候选、确认性研究、发布资格、提案、双人批准、发布授权和两阶段发布分层：链路更长，但能纠正、复现、审计、冻结和回滚。

## Consequences

- 牺牲“自动学习、快速调权”的速度，换取无静默漂移、可定位选择偏差和可安全撤销。
- `ProfileCandidateRevision`、`FeedbackStudy`、`ProfileChangeProposal`、`ProfileVersion` 和 `PublicationRevision` 是不同对象；分析完成、发布资格通过、提案获批、发布获授权、关键同步完成和权威指针提交分别是不同事实。Hiring Owner 与 HRBP/Profile Governance 批准必须来自两个不同的人类主体。
- 新画像默认只作用于声明的未来招聘周期；在途申请案件继续使用钉住版本。
- 画像生成、排名、淘汰和招聘决定永不开放 A3；自动监测和批准规则触发的安全冻结可以自主执行。
- 任职后数据属于额外处理目的，必须另有数据地图、权限、最小化、保留和公平审计批准，不能因已有 ATS/HRIS 接口自动进入学习链。
